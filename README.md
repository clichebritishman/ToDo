# Task Management Api

Written in ASP,NET Core Web API Leveraging Entity Framework Core for in memory database "persistence" .

## End Points 

### Get

We have a generic GetAll endpoint which accepts a status filter, if no filter is provided we simply return all values in the database. 

If a Status filter is accepted, as a Enum int value, 0 = Open, 1 = In Progress, 2 = Complete. We return entries from the database that is in the requested status. 

GET https://localhost:7022/Task/GetAll
GET https://localhost:7022/Task/GetAll?status=0
GET https://localhost:7022/Task/GetAll?status=1

### Post

For creation of a task we accept a Task json payload, outlining only the information we need such as the Title, Description and status. 

Id and Created date will be generated by the Api therefore does not require sending as part of the request payload. 

POST https://localhost:7022/Task/Create
Content-Type: application/json
{
  "title": "Start Work 34",
  "description": "Start working on the project 2123",
  "status": 0
}

POST https://localhost:7022/Task/Create
Content-Type: application/json
{
  "title": "Start Work 1232",
  "description": "Start working on the project 1232",
  "status": 0
}

POST https://localhost:7022/Task/Create
Content-Type: application/json
{
  "title": "Start Work asd2",
  "description": "Start working on the project as2",
  "status": 1
}

### Patch
For changing a status of a Task we send a patch request to the following URL task/{id}/{status} using the same Enum values as the Get request for status.

PATCH https://localhost:7022/task/1/2
Content-Type: application/json

# Time Limits 
Due to time limits in this instance I didn't write Unit Tests. However, I have purposely written my code using Interface abstractions, repository and service layer patterns so I can add unit tests easily and efficiently using MOQ and a preferred testing framework like Xunit.

	The code base follows clean Solid principles therefore I would keep expanding onto this foundation as per the requirements of the stake holder, once ready depending on user requirements, location, accessibility I would then host the Api via Cloud, or a private server accessible over VPN.
	
-   Where would you introduce persistence (e.g. a database) and why?
	
	The code base already uses a database provider via entity framework, in this instance as it's more of a POC I didn't opt for a full database provider like SQL. -   What would you change if the system needed to scale significantly?

	Code wise, I'd introduce Idompotency to ensure task duplication would not happen with a larger client base, however the project should serve as a solid foundation to expand upon. 

	Infrastructure side of things, it would depend on the amount of users, if it's a small internal tool, a single instance cloud host or a local vpn accessible self hosted solution would suffice.


-   How would you assign this work in a small team?

	Given the small scope for the POC there is not a lot to break down, however assuming a larger scope I would break down functionality into related logical chunks and assign them based on relevant experience and to try and minimise related areas intersecting to avoid dependencies on other work being completed before another developer can progress, however this isn't always viable. 

-   What would you improve with more time?

	I would add a solid unit test foundation, integration tests to ensure end to end functionality.
